# isoharness

isoharness is a website for stable isotope data reduction, one instrument at a time. EA-IRMS comes first: it corrects Thermo EA-IRMS carbon and nitrogen runs, with numbers from ea_irms, the Python engine behind the lab's EA-IRMS correction workbook, which this repository carries at version 1.4.11. GasBench N₂O (nitrate by the denitrifier method, and organic nitrogen after persulfate oxidation) and GasBench carbonate are planned.

## Where it stands

Phase one put the engine behind a web API, LibreOffice in the container image to compute the workbook's formulas, and the browser's preview port under a check against the engine in continuous integration. Phase two adds the web pages: a home page at `/` that lists the instruments, and the EA-IRMS page at `/ea-irms`, where you upload an export, or several at once, check the instrument's reference gas and background, go through the eight correction steps, each with its formula and one sample's arithmetic, and download the workbook, the results table, and the configuration, and for several runs the combined results. Each run can carry its operator, instrument, project, and notes, and a sample sheet can add each sample's own columns to every download. Anyone can use the page without signing in. Sign-in, saving, and history come in phase three. The service stores nothing; each upload is processed in a temporary folder that is removed before the response is sent. It runs at [isoharness.org](https://isoharness.org), on Google Cloud Run behind Firebase Hosting, and [DEPLOY.md](DEPLOY.md) has the steps.

## Running it

```
docker build -t isoharness .
docker run -p 8000:8000 isoharness
```

Then http://localhost:8000 is the home page, http://localhost:8000/ea-irms the EA-IRMS page, and http://localhost:8000/api/docs lists the endpoints and lets you try each one. Without Docker, `pip install -r requirements.txt` and `uvicorn isoharness.app:app` run the same service, but its workbooks carry formulas only unless LibreOffice (`soffice`) is on the PATH.

## The API

These endpoints serve the EA-IRMS page. An instrument added later gets endpoints of its own, and these keep their paths.

| Endpoint | Returns |
| --- | --- |
| `GET /api/health` | `{"status": "ok"}` |
| `GET /api/version` | The isoharness and ea_irms versions, and whether LibreOffice is present |
| `GET /api/defaults` | The package default configuration, in the form the POST endpoints accept |
| `GET /api/example` | The 2026-09-15 test run, which the page offers as an example |
| `GET /api/client` | The address the upload limit counts for this request, how many addresses `X-Forwarded-For` held, and `ISOHARNESS_PROXY_HOPS` (isoharness 0.4.1), for checking a deployment's proxies (DEPLOY.md, The upload limit) |
| `POST /api/process` | Every position's values and flags, the fitted steps, and the block the preview port recomputes from |
| `POST /api/workbook` | The correction workbook (.xlsx), with its formulas computed by LibreOffice unless `values=false` |
| `POST /api/results.csv` | The workbook's Results sheet as CSV, at full precision: each value followed by its 1σ (headed 1sigma), then Flags, the rerun mark with its reason and a suggested mass, the elemental drift factors, and %C and %N as measured |
| `GET /api/config-template` | The lab configuration as an Excel template, filled with the package defaults |
| `POST /api/config.xlsx` | A configuration sent as JSON, `{"config": {...}, "name": "run"}`, written as an Excel lab configuration; missing fields take the package defaults |
| `POST /api/config/read` | A lab configuration file, the Excel template or JSON, read into the form the other POST endpoints accept, with notes on anything filled from the defaults or left out |
| `POST /api/batch/results.xlsx` | Several runs' results in one Excel file (isoharness 0.2.0): Results, every position of every run with a Run column first; Runs, one row per run; Repeats, the samples measured in more than one run |
| `POST /api/batch/results.csv` | The combined Results sheet as CSV: Run, then the columns of `/api/results.csv`, at full precision |
| `POST /api/samplesheet/read` | A sample sheet (`file`, with `id_column` to choose its ID column) read, and the samples of the runs in `runs`, a JSON list such as `[{"name": "run.csv", "samples": [[20, "CI 3-2-H"]]}]`, matched to it: how each matched, which did not, the replicate groups, and the columns the results would carry (isoharness 0.3.0) |
| `POST /api/samplesheet/template.xlsx` | A sample sheet to fill in, with one row per name in the JSON body `{"names": [...]}` |

Each POST takes a multipart form with `file`, an export as .xls, .xlsx, .xlsm, .csv, .txt, or .tsv of at most 10 MB (`ISOHARNESS_MAX_UPLOAD_MB` changes the limit), and optionally `config`, a lab configuration as JSON in the form `/api/defaults` returns, read from ea_irms 1.4.10 by the rules of the Excel one: a value it cannot use is refused (422) with the setting named, and a key it does not read is left out with a note. `/api/workbook` also takes `run_name` and `run_date` for its Setup sheet. A file ea_irms cannot read is refused with a message that names the problem, such as the columns it lacks. The two batch endpoints take the exports in `files` instead, at most 20 in a request (`ISOHARNESS_MAX_BATCH_RUNS`) and 10 MB together; `configs`, a JSON list with one configuration per file, in order, or one JSON object for all of them; `run_dates`, a JSON list of dates or nulls; and, for the Excel file, `config_name`, the name of the lab configuration to print on its README sheet. From isoharness 0.3.0 `/api/process`, `/api/workbook`, `/api/results.csv`, and the two batch endpoints also take `sample_sheet`, a sample sheet as .xlsx, .xlsm, .xls, .csv, .tsv, or .txt, with `id_column` to name its ID column, and `/api/process` and `/api/workbook` take `run_info`, a JSON object with any of Operator, Instrument, Project, and Notes; the batch endpoints take `run_infos`, a JSON list with one such object per file, or one object for all of them. The sheet is read for that request only. Each counts as one upload toward the hourly limit, however many files it carries. From isoharness 0.2.0 the limit is 600 uploads per address in an hour (`ISOHARNESS_READS_PER_HOUR`) for every POST endpoint but the workbook, and 60 for the workbook (`ISOHARNESS_UPLOADS_PER_HOUR`), the one LibreOffice computes.

The service converts one workbook at a time, because LibreOffice conversions that run together share a profile; in a test on 2026-10-11, one of three conversions started together failed, so the image runs a single service process. Three requests sent together came back in 5.1, 6.8, and 8.5 s, one after another. From isoharness 0.4.1 a workbook request waits at most 45 s for its turn and at most three wait at once (DEPLOY.md, Workbook requests); the next is told to try again in a minute. The image starts LibreOffice once while it is built, which in a test on 2026-10-11 brought the first workbook from a fresh container down from 3.42 s to 2.47 s (one trial each).

## Several runs at once (isoharness 0.2.0)

The EA-IRMS page takes several exports at once, chosen together or dropped together, up to 20 runs. Each is sent to `/api/process` on its own and corrected on its own, with the standards in that run; one lab configuration applies to all of them, and choosing another processes every run again, or none if any is refused. Each run keeps its own choices: the batch list on the upload screen and the run list under the run's name beside the steps show any run on the screen where you are, with the choices it was left with, and an export with the name of a run already in the batch replaces that run. The run date of each comes from its file name, and the date field sets the date of the run shown. On the Results screen, the downloads add the combined results, an Excel file, and the combined results table, a CSV file; a section below the samples lists every run with the corrections in force and a button for its own workbook, and the samples measured in more than one run, matched by name, with the mean, SD, and range of their δ¹⁵N and δ¹³C. The workbooks are still built one run per request.

The combined results come from `isoharness/batch.py`, which corrects nothing itself: it puts each run's Results rows, from the engine, one run after another with the run's file name in a Run column first; writes one row per run on the Runs sheet (file, run date, counts of positions, which corrections were in force, the calibration slopes, the samples marked for a rerun or a check, and the problems of the whole run); and lists on the Repeats sheet every analysis of a sample, or of a check standard, whose name appears in more than one run, with its difference from the mean of that name's analyses. A sample is matched by its identifier, ignoring case and surrounding spaces, and a check standard by its row of the standards table. The Results values are numbers, not formulas, at the 16 significant digits an Excel file keeps; the CSV file keeps every digit. Differences between runs are not part of any 1σ.

## Run information and a sample sheet (isoharness 0.3.0, ea_irms 1.4.8)

Each run on the EA-IRMS page can carry four short texts, Operator, Instrument, Project, and Notes, typed on the upload screen for the run shown, kept with it like its run date, and copied to every run with one button. They are written on the workbook's Metadata sheet (Operator also in Setup B7, the cell that read Analyst before 1.4.8) and after the earlier columns of the Runs sheet of the combined results, only the fields some run has.

A sample sheet holds one row per sample: an ID column and any others, such as project, site, species or material, fraction, collection date, depth, and notes. The page offers one to fill in, with the batch's sample names in its ID column and those columns after it, and reads the lab's own .xlsx or .csv file as well: the sheet named Samples or the first, the header found below a title line, the ID column chosen on the page or guessed from its name. A Sample position matches a row when its identifier equals the row's ID, or begins with it followed by a character that is neither a letter nor a digit, so that CI 3-2 matches CI 3-2-S and CI 3-2 H but not CI 3-20; when several IDs fit, the longest wins, and case, spaces at either end, and runs of spaces are ignored. When no ID fits as written, the spaces are taken out of the name and the IDs and they are compared again, so that PD1-H matches PD 1 (Tony Wang's choice of 2026-10-13, after three analyses of one colony missed a sheet that wrote PD 1). Standards and blanks are not matched. The page lists how each sample matched and which did not. The results table, the combined results (Excel and CSV), and each workbook's Results sheet carry, after their own columns, the ID a sample matched (Sample ID (sheet)), how it matched (exact, prefix, either followed by ", spaces ignored", or not in sheet), and each column of the sheet that holds a value for a sample of the run or batch, renamed with " (sheet)" where the table already has the name; each workbook also has a Metadata sheet with the run information and the run's samples, and Results reads it only at positions whose identifier is still the one matched. The sheet stays in the browser and goes with each download; the server reads it for that request and keeps nothing. On the command line, `python -m ea_irms run.xls --samples samples.xlsx` (with `--id-column` to name the ID column) builds the workbook with it.

Analyses of one sample in one run are replicates: Sample positions matched to the sheet with the same identifier, or matched by their own name to rows with the same value in the sheet's Replicate of column, which names the sample an analysis repeats. Fractions of one colony that only share a shorter ID, such as CI 3-2-H and CI 3-2-S, are not, and from ea_irms 1.4.10 a sample matched by an ID its name begins with, such as CI 2-2-H+S by a row for CI 2-2-H, takes that row's columns but not its Replicate of, so it is a replicate only of samples with its own name (Tony Wang's choice of 2026-10-14, keeping the matching rule as it was). ea_irms compares each group's range in δ¹⁵N and in δ¹³C with the critical range of ISO 5725-6 (section 5.2), f(n) × s, where s is the repeatability of one analysis in use (`u_sample_n` and `u_sample_c`, or the pooled scatter of the anchor replicates, the term 1σ uses) times the calibration slope, and f(n) is the 0.95 quantile of the range of n values from one normal distribution in units of its SD: 2.77 for two analyses, the factor ISO 5725-6 rounds to 2.8 in r = 2.8 s, then 3.31 for three and 3.63 for four (`ea_irms.metadata.CRITICAL_RANGE`, computed by integration and checked against SciPy to 1e-6). n counts the analyses with a value. When the range is above it, every analysis of the group is marked for a rerun of that element, with a reason such as "replicates at positions 31, 32, 33 differ by 0.60 in d15N, above 0.57", since the data cannot say which analysis is off; the standard's next step is more analyses and their median. `rerun_replicates` (Setup B71) switches the marks off, and without a sample sheet nothing is compared. The workbook's Replicates sheet shows each group with its range and limit as formulas. The rule is Tony Wang's of 2026-10-13, the replicate rule of the 1.4.4 rerun marks, which waited for the sample sheet; the unrounded factors are the default named with it.

## Explanations in each step (isoharness 0.4.0, ea_irms 1.4.9)

Each correction step on the EA-IRMS page, from the blank to the uncertainty, explains itself under its figures. It says what the correction does, gives its formula, and takes one sample's numbers through that formula in the run's own values; this worked example follows the sample selected on a figure or in the sequence, and until one is chosen it uses the first sample with a value. The blank, linearity, and drift steps also draw each sample's change in its final δ¹⁵N and δ¹³C from that correction, the value with the correction minus the value without it, against ±kσ of that sample (2σ by default). The explanations are shown until a reader hides them, and the browser keeps that choice (`localStorage`, key `isoharness.explanations`). Each quality check sits in the step it belongs to, so the linearity step shows the effect of the linearity choice and the sample size against the size series, the drift step the effect of the drift choice and whether the drift monitors agree, the calibration step whether the anchors bracket the samples and the check standard, and the elemental content step the largest bias among the monitors in %N or %C. The Quality checks step lists them all, with a button back to each step. ea_irms 1.4.9 changes only the wording of the workbook and of the two templates, the lab configuration and the sample sheet; every number is as in 1.4.8.

## Fixes from the review of 2026-10-14 (isoharness 0.4.1, ea_irms 1.4.10)

A review of the code and the site on 2026-10-14 by four independent reviewers, each finding reproduced or read in the code before it was reported, found 6 High and 14 Medium problems, and this version fixes all 20. `tests/test_review_fixes.py` holds the fixes in the engine, the files, and the service in place, each test named by its finding, and `scripts/e2e_web.py` checks three of the page's in a browser (R-03, R-08, and R-17).

The numbers:

- R-01. The calibration needs anchors of two materials with different accepted values. With only one, as when the standards table lacks one of the two anchors, nothing is calibrated, and the top line of the Rerun sheet says why; before, every sample took that material's accepted value, with a small 1σ and no flag.
- R-07. A JSON configuration is read by the rules of the Excel one, by the service and on the command line: On, Off, and Auto in any case, positions as a list or as text such as 40, 47 or 40 47, finite numbers inside each setting's range, and anything else refused with the setting named. Before, "off" ran as Auto in the engine and as Off in the workbook.
- R-08. The first drift position, the positions left out, and a repeatability taken from the drift monitors are decisions about one run's positions. A configuration downloaded from the page names its run (`run_file`, the last row of Settings) and where its repeatability came from (`u_sample_n_source` and `u_sample_c_source`, Drift monitors or empty), and those values are applied only to a run of that name, compared in any case and with or without the export's extension (.xls, .xlsx, .xlsm, .csv, .txt, or .tsv), so two runs exported under one name count as one. Any other run gets none of them; where the repeatability came from the drift monitors, the page takes the SD of that run's own monitors. A configuration that names no run, as none did before 1.4.10, still applies them to the one run it is used with, with a note to check that they belong to it, and to no run when it is given to several at once: on the page when several exports are added together or several runs are open, and in the batch endpoints when `configs` is one object for all the files. On the page such a configuration goes with the first run it is used with and with none added later. The page shows these notes on its upload screen; through the API they come back in `config_notes` from `/api/process`, in the `X-Isoharness-Config-Notes` header of the file downloads, under the title of the workbook's Setup sheet, and in a Configuration notes column of the combined results' Runs sheet (`ea_irms.scope_to_run`). The page's own downloads name each run, so they carry none. A repeatability saved before 1.4.10 does not say where it came from, so it is still taken as the lab's own value. Before, one run's exclusions were carried to every run of a batch.
- R-09. A peak at or below the intercept of the k-factor line holds no N or C that the line can detect, so the position reports no %N (or %C) and no C:N, and Flags reads %N below detection; before, one of the reference runs kept outside this repository read a negative %N with a negative 1σ.
- R-10. The suggested rerun mass reads the analysis's peak area per mg above the blank, not the whole peak, and says when the mass needed is more than the heaviest capsule in the run. On the same reference run the old rule suggested 95.4 to 299.2 mg where about 1,728 mg would be needed (calculated).
- R-11. A sample matched by an ID its name begins with takes that row's columns but not its Replicate of, so it is a replicate only of samples with its own name (see Run information and a sample sheet).
- R-13. The reference-gas SD and the check of the reference pulse at each position read every pulse Isodat did not designate, two of CO₂ at each position in a full export. On the test run the CO₂ SD is 0.082‰ over all 112 pulses, against 0.065‰ from the first pulse at each position alone.
- R-20. The carbon blank correction had never run on any data. `scripts/port_cases.py --with-carbon-blank` gives each blank capsule of a run a sample CO₂ peak (made-up values), and the tests run the engine, the workbook, and the preview port on it.
- R-21, a Low finding fixed with them. The engine rounds the numbers in its flag texts as Excel does, half away from zero at the last place, so the two agree at an exact half.

The files:

- R-02. The workbook is sized from the export, up to positions 1 to 400 and 4,000 peak records, and an export that needs more is refused with the reason. Before, the workbook left out positions above 120 and records past 1,000 without saying so.
- R-04. An .xlsx upload is checked before it is opened (`ea_irms/xlsxguard.py`): one that unpacks to more than 25 MB, 5 MB for a lab configuration, or holds more than 500 files is refused. The readers of an export and of a sample sheet then stream the sheet, refuse more than 20,000 rows, and read at most 256 columns of an export and 60 of a sample sheet; a lab configuration, at most 5 MB unpacked, is read whole. The review built a 5.0 MB file that unpacks to 121 MB and took 2,872 MB of memory to read, against the service's 1 GiB.
- R-06. Text from an upload (identifiers, the sample sheet's cells, the run information, the configuration's text, and file names) stays text in every workbook (`ea_irms/cells.py`), and a CSV cell that a spreadsheet would read as a formula gets a leading apostrophe. Before, a sample named =1+1 reached the workbook as a formula, which the server computed.

The service:

- R-05. The upload limit counts the visitor's address, `ISOHARNESS_PROXY_HOPS` places from the right of `X-Forwarded-For` (2 by default, for Firebase Hosting and Cloud Run's front end, still to be checked on the deployment), so on that path a header a client makes up no longer resets it. A request sent to the `run.app` address itself passes one proxy fewer, and there a client can still choose the address it is counted under; the cap of one instance and the spend cap bound what that costs. `GET /api/client` shows what a deployment reads (DEPLOY.md, The upload limit).
- R-12. A setting that is not a finite number in its range, or not of the right kind, is refused (422) with the setting named, and so is a standards-table entry that is not a finite number, a %C or %N outside 0 to 100, or a negative 1σ; before, NaN, Infinity, or text where a list belongs gave a server error, and a negative k was taken.
- R-16. A workbook request waits a limited time for LibreOffice, and a stuck LibreOffice is stopped with everything it started (DEPLOY.md, Workbook requests).

The page:

- R-03. Each point of a figure has a button no wider than the distance to its nearest neighbor and no narrower than its dot, so a click selects or leaves out the point under the pointer, and the message bar names the position that changed.
- R-14. On a phone, numbers no longer break across lines or print over their labels, and a table that scrolls sideways shows that it does.
- R-15. A figure's points and the sequence are each one stop for the Tab key, with the arrow keys, Home, and End moving along them; a new screen's heading takes the focus; and the samples table is a table of rows and cells.
- R-17. With a run on the page, the browser asks before the page is left or reloaded, since the runs live only in that tab.
- R-18. A message that something failed is an alert, and it sits in view at the bottom of the screen on a phone.
- R-19. In Windows high-contrast mode the chosen setting of each switch and the sequence strip keep their marks.

## Peaks in Peak Nr order (isoharness 0.4.2, ea_irms 1.4.11)

An export can list each position's peaks from the last to the first, with the TCD rows after them, and a run tested on 2026-10-14 did so at every position. Up to 1.4.10 the engine read a position's peaks in the order of the file, so in such an export it took an undesignated reference pulse for the sample N2 peak and another for the sample CO2 peak. From 1.4.11 each position's peaks are put in Peak Nr order before they are identified, and they are identified as before, by the Is Ref flag and by which amplitude column is filled; Peak Nr sets the order and never says which peak is which. The workbook needed no change, because its formulas find each peak by its Peak Nr value (the Key column on Raw); its Raw sheet keeps the records in the export's order. `tests/test_peak_order.py` writes the 2026-09-15 run with each position's records reversed, and shuffled with five seeds, and holds the parser, the corrections, `/api/process`, and the workbook to the run as exported; with the 1.4.10 parser, 9 of its 11 tests fail. On 15 other exports, whose peaks run in Peak Nr order, 1.4.11 reads the same peaks as 1.4.10, so every value is unchanged.

## Four findings of 2026-10-14 (isoharness 0.4.3, ea_irms 1.4.12)

Seven runs of another project, put through isoharness.org on 2026-10-14, showed four more things to change. The limits and the method below are Tony's choices of that day.

- W-09. Where two or more unflagged CO2 peaks come before a position's first designated CO2 pulse, the engine took the one next to the pulse and the workbook the first one, so the two gave that position different carbon values. The workbook now takes the one next to the pulse too (Work column J), and Flags says how many came before it, for example "2 CO2 peaks before the reference pulse, the last one used".
- W-10. A material analyzed once has no scatter of its own, so up to 1.4.11 the error of its mean counted as 0, and a run whose calibration rested on one analysis of an anchor material reported a 1σ that was too small. That term now takes the repeatability in use, Setup B30 or B31, or else the pooled SD of the materials analyzed more than once (Fits rows 136 and 156), and the engine's uncertainty budget names the source of each material's term.
- W-03. In a filtered export the designated pulses' amplitude is interpolated between the positions that carry one and held flat before the first and after the last, where it cannot follow the pulses' drift. A run whose only designated pulses came at its end therefore kept its first no-gas CO2 peaks, a few percent below that amplitude, as sample carbon. Positions before the first and after the last designated pulse now use a tolerance of their own, `ref_pulse_ampl_tol_outside` (Setup B41), 5% by default and never narrower than the tolerance between them, which stays at 2% (`ref_pulse_ampl_tol`, Setup B39).
- W-02. Nothing judged the calibration line itself. Its slope against 1 and the anchors' residual SD about it are now judged at two levels, a Note when the slope is more than 0.05 from 1 or the SD above 0.3 permil, and a Caution beyond 0.10 or 1.0 permil (`cal_slope_note`, `cal_slope_caution`, `cal_sd_note`, `cal_sd_caution`; Setup B73 to B76). Either level is a problem of the whole run on the Rerun sheet and in the Runs sheet of the combined results, QC rows 23 and 25 give the level, and the page's Calibration step shows the check.

A review of the change before release found three more things, fixed in the same version. A lab configuration written before 1.4.12 has no `ref_pulse_ampl_tol_outside` and takes 0.05, so with `ref_pulse_ampl_tol` above 0.05 the tolerance outside the span would have been the narrower one; the wider of the two now applies there. A repeatability of 0 reached Setup B30 and B31 as an empty cell, so the workbook used the pooled SD where the engine used 0. A limit below 0.0001, such as 0.00005, read 5e-05 in the engine's text and 0.00005 in the workbook's; both now write plain decimals, and the residual SD has 3 decimals in both, as Fits rows 362 and 365 show it. The workbook's Flags also list each position's flags in the engine's order now, the N peak's before the C peak's and the elemental exclusion before the blank multiples, and the tests compare flags as lists.

`tests/test_findings_1412.py` writes a copy of the 2026-09-15 run that shows each case and holds the engine, the workbook, and the preview port to it. On the nine reference runs, each with its own configuration, 1.4.12 gives every value 1.4.11 gives. The changes there are that the run whose carbon measurement failed now lists its carbon calibration line among the problems of the whole run, and that the workbook lists the flags of 18 positions in the engine's order, the same flags as before.

## Uncertainty of %N, %C, and C:N (ea_irms 1.4.3)

Each %N, %C, and C:N carries a 1σ. For %N and %C, 1σ combines five terms, each a fraction of the value: the instrument's repeatability, from the drift monitors' measured over certified ratios by successive differences in position, less the part their own weighing explains; the position's weighing, the balance's standard uncertainty (`balance_u_mg`, Setup B33) over its mass; the calibration, the interpolated elemental drift factor when that correction is in force and the k-factor line at the position's micrograms when it is not; the certificate uncertainty of the material that sets the scale (standards table columns 1σ(%C) and 1σ(%N)); and trueness, the anchors' RMS deviation from their certified values combined with their certificate uncertainty, as in the Nordtest TR 537 handbook. C:N takes the same terms without the weighing, which cancels in a ratio. Empty inputs count as 0. The workbook computes every term as a formula (Fits rows 300 to 335), and QC counts the anchors and linearity standards that fall within k × 1σ of their certified values. The page does not show these yet.

## Uncertainty as 1σ (ea_irms 1.4.5)

Every uncertainty that the workbook, the results table, and the page report is one standard deviation, 1σ, the combined standard uncertainty; up to 1.4.4 the workbook put the expanded uncertainty U = k·u beside each value and the u columns after Flags, and from 1.4.5 it puts 1σ beside each value and drops the separate block, so the elemental drift factors and the values as measured move from AA to AD to U to X. The checks still compare against k × 1σ, with k (`coverage_k`, Setup B32) 2 by default: the anchors and linearity standards within it on QC, the anchors outside it among the problems of the whole run on the Rerun sheet, and the page's counts of samples that reversing a correction would move by more than it. The results table heads its columns 1sigma(...) rather than 1σ(...), since Excel misreads a Greek letter in a CSV file that has no byte-order mark. The engine and the API keep their names, `u_*` for 1σ and `U_*` for k × 1σ.

## The lab configuration as an Excel file (ea_irms 1.4.6)

A lab configuration can be an Excel file as well as JSON. `ea_irms/labconfig.py` writes it with three sheets: README; Settings, one row per setting with its value, what it means, and a grey Key column that is how the file is read; and Standards, the standards table in the column order of the workbook's Setup sheet, at most 16 rows. The page offers the template, filled with the package defaults, on the upload screen, and reads a chosen .xlsx file through `/api/config/read`; the Configuration download after a run is the same Excel file with that run's choices, and a .json configuration still works. On the command line, `python -m ea_irms --write-config lab.xlsx` writes the template and `--config lab.xlsx` reads one. An empty cell means off or not given where the setting allows that, as on the Setup sheet; where it does not, an empty cell is refused rather than replaced by a default. Every cell that cannot be used is named in one message, such as `Settings B6 (blank_correction) is 'maybe'; it needs one of On, Off, Auto`. A row missing from the file, as in one written by an older version, takes the package default, and a key this version does not read is left out; both are reported as notes. The last rows of Settings (the first drift position and the positions left out) belong to one run, and so does a repeatability taken from that run's drift monitors; from ea_irms 1.4.10 the file names that run in its last row (see Fixes from the review of 2026-10-14). An Excel file keeps 16 significant digits, so a value computed to more digits, such as the drift monitors' SD saved as the sample repeatability, comes back changed in the 16th or 17th digit; over 200,000 random values the largest relative change was 5.6e-16.

## Rerun marks (ea_irms 1.4.4, 1.4.7, and 1.4.8)

A sample is marked for what measuring it again can fix: the amount, the peak, or the state of the instrument at its position. It is marked for a rerun of N, C, or both when its peak lies below the range of the linearity standards or under the blank multiple (`min_blank_multiple`, 3 by default); when its peak reaches the instrument's largest amplitude (`max_amplitude_mv`, 50,000 mV by default, Setup B69); when it follows an oversized sample and its background rose by more than `carryover_mv` (2.0 mV by default), or when an undesignated N2 or CO2 reference pulse at its position lies more than `ref_pulse_off_sd` robust SDs (4 by default) from the median of the run's pulses (from 1.4.10 every such pulse counts, not only the first at each position); or when the 1σ of its final δ¹⁵N or δ¹³C is above `rerun_max_1sigma` (0.5‰ by default, Setup B70), which a run with better anchors can fix. Both 1.4.7 rules are Tony Wang's of 2026-10-13: a peak above the linearity range but under the instrument's largest amplitude is no longer marked, though it keeps its flag, and with `max_amplitude_mv` empty every peak above the range is marked, as before 1.4.7. The 1σ leaves out the blank, linearity, and drift corrections, so a peak above the range whose linearity correction is extrapolated is not caught by it. It is marked for a check when it ran before the background settled or carries the peak of only one element. A δ value outside the anchors' range stays a flag and is not marked, because a rerun would extrapolate the same way.

For a rerun the workbook suggests a mass range that puts each peak inside the linearity range and above the blank multiple, from that analysis's own peak area per mg above the blank (from 1.4.10), and says when that is more than the heaviest capsule in the run; when no one mass suits both N and C, it gives both ranges for two capsules. Problems of the whole run are listed once, at the top of a new Rerun sheet: a check standard further than `check_offset_permil` from its accepted value, anchors outside k × 1σ (2σ by default) for %N, %C, or C:N, a reference-gas SD at or above `ref_gas_sd_limit` (0.1 permil by default, the zero-enrichment limit of the FIRMS Good Practice Guide, 2nd ed., section 4.3.2), and, from 1.4.10, an element with no calibration. Results carries the mark, its reason, and the suggested mass after Flags, with rows shaded orange (rerun) or pale orange (check), and the Rerun sheet lists the marked samples in the order they ran. From 1.4.8 replicates named by a sample sheet are compared too (see Run information and a sample sheet). The page does not show the marks yet.

## The preview port

`port/engine.js` recomputes blank, linearity, drift, calibration, elemental content, and the uncertainties in the browser, so the page redraws on every switch, while the API's values stay the ones downloaded. It reads the user's decisions (the switches, the drift model, exclusions, and the sample repeatability) and, from the block's `settings`, the configuration's settings that act inside those steps (the significance level, the monitor outlier limit, the check-standard offset, the blank multiple, the multiple k of 1σ that the checks use, the elemental gate, and the first drift position). Each position in the block also says whether the server set its CO2 peak aside as a reference pulse, which the port flags as the engine does. Settings that act before the block is built (the standards, the size limits, settling, carryover, and the reference-pulse windows) are applied by the server, so the page sends a newly loaded configuration back to `/api/process`.

On every upload the page also runs the port on the configuration's own decisions and compares each position's corrected values, uncertainties, %N, %C, C:N, elemental factors, and flags with the engine's from `/api/process`; the upload screen says whether they agree, and the steps warn when they do not.

The port check runs the engine on 643 decision sets with the configuration's settings (all 243 combinations of the switches and the drift model, then 400 random sets) and 360 more under twelve non-default settings, and requires the port to agree within 1e-9 relative on every value, flag list, and fit. Continuous integration runs it three ways on the 2026-09-15 test run: as exported, with a configuration that makes the acetanilide bypasses a check standard (`tests/data/config_check_standard.json`, accepted values set 0.3‰ from the run's own mean so that the check offset matters), and rewritten as a filtered export, so that the reference-pulse check sets CO2 peaks aside.

## Checks

The tests run with `pip install -r requirements-dev.txt` and `python -m pytest`. The store and isolation tests need Postgres at `EA_TEST_SUPER_DSN` and `EA_TEST_APP_DSN` (see `.github/workflows/ci.yml`), with a UTF8 database, since a SQL_ASCII one returns text as bytes and fails seven of them; the workbook tests need LibreOffice.

`python scripts/smoke.py http://localhost:8000 tests/data/20260915_raw.csv` checks a running service, requiring the workbook it returns to have its formulas computed and to hold the values `/api/process` returned.

`python scripts/e2e_web.py` checks the page end to end: it starts the service on a free port, opens the home page and follows its link to the EA-IRMS page, drives that page in Chromium through the upload, a lab configuration, all ten screens from the instrument step to the results with each correction step's explanation and checks, five decisions, a batch of three runs with the combined results, run information and a sample sheet carried into the combined results and a run's workbook, one run's downloaded configuration kept to that run in a batch, and the landing page's example run, and requires every value on the results screen to equal, to the shown precision, the results table the service returns for the same decisions built without the page, and the downloaded configuration to reproduce it. It fails on any console error or failed request, and saves screenshots (`--shots`). With `--url` it checks a service already running, such as the image or a deployment. It needs Playwright for Python (in `requirements-dev.txt`) with its Chromium (`python -m playwright install chromium`), and LibreOffice.

`python scripts/reference_check.py MANIFEST.json --url http://localhost:8000` is the engine check before a release, on reference runs that stay outside this repository (the manifest format is in the script). On each run the API's values must equal its workbook, they must equal ea_irms called directly, and the workbook must equal the one delivered from the same export, cell by cell.
